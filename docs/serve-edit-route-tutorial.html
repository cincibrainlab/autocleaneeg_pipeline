Edit tutorial

Edit an existing route without making Production scary.

This tutorial is for the moment after the first route already exists and something needs to change. The key question is not just “how do I edit it?” It is “should I edit this route at all, or should this become a new Draft route instead?”

1. Decide edit vs create

Use this decision first.

Edit the existing route when

  • the route is still the same job
  • you are fixing folder, glob, or naming details
  • you want the existing route to evolve in place

Pause and think when

  • the route already runs in Production
  • the change affects which files will match
  • someone else depends on the current live behavior

Create a new Draft route when

  • the workflow is meaningfully different
  • live behavior must stay untouched for now
  • you would describe it as “basically a different job”
2. Update the route in Draft

Use the same route id if it is still the same route.

The safe way to edit a route is still serve route upsert. Re-running it is normal. That is the idempotent model.

Terminal
autocleaneeg-pipeline serve route upsert \
  resting-biosemi64 \
  --path /path/to/serve-workspace \
  --mode test \
  --taskfile /path/to/RestingEyesOpen.py \
  --montage biosemi64 \
  --ingestion-folder /data/incoming/resting-updated \
  --file-glob "*_rest.set" \
  --recursive \
  --enabled

Why this is safe

The route spec is updated in place and the generated configs are rebuilt deterministically. Repeating the command is expected, not a failure state.

TUI help

After the update, use the route screen to inspect the route, verify the details, and sync if needed.

3. Validate again

Do not assume a small edit is harmless.

Terminal
autocleaneeg-pipeline serve validate \
  --path /path/to/serve-workspace \
  --mode test

Good result

The route validates cleanly and the new folder/glob/task still describe the same job you intended.

Bad result

If validation fails, do not improvise a live edit. Fix the route definition and rerun the same Draft update path until it is clean.

4. Handle Production carefully

The hard part is not syntax. It is protecting live behavior.

If the route is Draft only

Edit it freely, validate again, exercise it safely, then promote it later.

If the route is already in Production

If the change would alter live behavior before you are ready, do not reuse the live route casually. Make a new Draft route instead and prove it there first.

Practical rule

If you need live to stay exactly as it is today, do not treat this as a harmless edit. Treat it as a new Draft route until it earns promotion.

5. Common mistakes

These are the route-edit traps to avoid.

Editing the live route casually

This is how Production becomes experimental without anyone admitting it.

Creating a new queue instead of a new route

The problem is route identity, not queue count.

Cloning the route just because one field changed

If it is still the same job, keep the same route id and update it in Draft.
