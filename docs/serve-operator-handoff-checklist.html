Operator handoff checklist

Hand off the serve workflow only when this page stays boring.

This SOP checklist is for the moment when a technical lead hands the serve workflow to lab operators. The goal is not “it runs on my machine.” The goal is that another person can run it, monitor it, and know when to escalate.

For operators

Use this page as the day-to-day checklist once the workflow is already set up and documented.

For technical leads

Use this page before handoff to confirm the route setup is explainable, validated, and supported.

What this page assumes

The workspace exists, at least one route has already been proven in Draft, and the team has agreed who owns escalations.

Before handoff

Do not hand this off until these are true.

A handoff is ready only when the route behavior, the operator workflow, and the escalation path are all explicit. If any of these are still fuzzy, this is still a technical lead problem.

Workflow readiness

The workspace path is known and documented.
Each active route has a clear name, task, montage, and watched folder.
The route has been proven in Draft before any Production promotion.
The operator can explain what files should arrive and what output should happen next.

Operator readiness

The operator has used the TUI Routes screen at least once.
The operator knows the difference between Draft and Production.
The operator knows how to validate after a route update.
The operator knows which issues are normal warnings versus escalation triggers.

Support readiness

A technical lead is explicitly named as the escalation owner.
The operator knows where the guide, tutorial, and portal live.
The team agrees whether operators may only toggle/promote routes or may also change route definitions.
Someone owns Production incidents outside operator hours.
Daily checks

Five-minute operator sweep.

This is the lightweight routine for a workflow that should feel stable. If daily checks become long or confusing, the handoff was premature.

Route view

Check the route state

  • Are the expected routes still present?
  • Are Production routes still enabled?
  • Is anything unexpectedly stuck in Draft only?
Queue and activity view

Check for obvious drift

  • Are files moving through the expected work states?
  • Did any route start failing when it was stable yesterday?
  • Is there a repeated warning tied to one route name?
When to stop

Escalate instead of experimenting

  • Do not invent a new route during daily operations.
  • Do not clone near-identical routes to “see if it helps.”
  • Do not bypass Draft if a Production route needs real changes.
Weekly checks

Fifteen- to twenty-minute review.

Weekly review is where a technical lead checks that the system remains explainable, not just technically alive.

Review active routes

  • Remove or disable routes that are no longer needed.
  • Confirm route names still match their actual task and montage.
  • Check that watched folders are still the intended folders.

Review handoff quality

  • Can a second person explain the same routes the same way?
  • Are operators relying on undocumented manual tricks?
  • Do the linked docs still match the real workflow?
Escalation map

Who to escalate to and when.

Replace these role descriptions with actual names in your team process. The page keeps the role logic explicit even if the people change.

Operator can usually handle

Normal operating actions

  • checking route state
  • syncing generated configs
  • enabling or disabling a route with prior approval
  • using the tutorial or guide to confirm the intended workflow
Escalate to technical lead

Configuration or route problems

  • a route that used to work now fails validation
  • a watched folder or task file changed unexpectedly
  • Production behavior needs a real route change
  • operators are unsure whether to edit an existing route or create a new one
Escalate immediately

Production-risk situations

  • files are not being processed in Production when they should be
  • wrong task or montage is being applied to real incoming data
  • outputs look materially wrong or incomplete
  • there is no clear owner available for the incident
