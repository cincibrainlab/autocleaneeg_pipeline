Operator guide

Run serve with routes, not guesswork.

The new serve model is designed for operators. You define a route once, validate it in Draft, then promote it to Production. Re-running setup is safe: if nothing changed, nothing moves; if something changed, only that route is updated.

Draft = safe proving ground
Production = live processing
Safe rerun = repeat without duplication
The short version

One route describes one kind of incoming work.

A route is the operational unit. It describes where files arrive, what task should run, which montage to use, and whether that setup is still in Draft or already approved for Production.

Think in routes

One route per task-and-montage combination. You do not need a separate queue for every combination.

Only two lanes

Behind the scenes there are only two processing lanes: Draft and Production. In the current system these map to test and live.

Repeat is safe

Running setup again should not duplicate finished work or wipe history. It simply confirms or updates the route definition.

1. Draft vs Production

Use Draft to prove a route. Use Production to trust it.

The biggest usability shift is that operators no longer need to think in raw queue files. Think in two lanes instead: a safe lane for proving a route and a live lane for real work.

Draft

Where you try things safely

  • Use this while creating a new route.
  • Validate folders, task selection, montage, and file readiness rules.
  • Watch for obvious mistakes before you trust the route with live intake.
  • Good for dry runs, sample files, and operator review.
Promote when stable →
Production

Where approved routes process real work

  • Only move a route here after Draft behaves as expected.
  • Production should be boring, predictable, and easy to monitor.
  • Keep changes small. If you need to experiment, go back to Draft first.
  • Operators should be able to explain every active Production route.
Good rule of thumb If you would feel nervous explaining a route to someone else, it still belongs in Draft.
2. Route-first model

A route is the thing you manage.

A route is a clean promise: “When files like this appear in this place, run this task with this montage.” That is easier to reason about than creating many separate queues.

Route anatomy

What every route needs

Route name
Human-readable label Example: “AuditoryOddball 128ch” or “Resting Eyes Closed 64ch”
Input location
Which folder to watch The place where finished files arrive
Task
Which workflow to run The experimental task or processing recipe
Montage
Which channel layout applies The expected cap or channel structure for these files
Ready rule
When the file is safe to pick up Examples: file size stable, sidecar present, upload complete
Why this is scalable

10 to 20 combinations still stay manageable.

You can have many routes while still using only two processing lanes. That keeps monitoring simple without flattening meaningful differences between tasks.

What not to do

Do not create a new queue for every montage.

Queues are operational lanes. Routes are configuration units. Keep those roles separate so the system stays understandable.

Operator test

If you can explain the route card, you can operate it.

That is the right standard for a non-technical team member covering intake or review.

3. Step-by-step setup

Build a route once, then promote it when it proves itself.

This is the operator path. It is intentionally repetitive and safe. The goal is not speed on the first run. The goal is confidence and clean handoff later.

01

Name the route in plain language

Use the task and montage in the name so anyone can recognize it later. Good names reduce support questions.

02

Choose the input folder and ready rule

Decide where the files appear and how the service will know they are complete. This is the most important safety setting.

03

Select the task and montage

These tell the system how to process the files. One route should describe one clear task-and-montage combination.

04

Validate in Draft

Run the route in the safe lane first. Use sample files or dry runs until the route behaves exactly the way you expect.

05

Promote to Production

Once the route is boring and predictable, move it into live use. Promotion should feel like approval, not experimentation.

06

Repeat the same process for new routes

Do not mutate old routes into completely different ones. Create or update routes deliberately so the history stays easy to read.

What success looks like A new team member should be able to answer three questions from the route card alone: what arrives, what runs, and whether it is still in Draft or already trusted in Production.
4. Safe reruns

Re-running setup should be calm, not scary.

The route-first workflow should be idempotent. That means you can run setup again without creating duplicate jobs or destroying past work. Operators need this because folders change, task details change, and names sometimes need cleanup.

What a safe rerun should do

  • Create the route if it does not exist yet.
  • Update only the fields that changed.
  • Leave queue history and prior outputs alone.
  • Do nothing visible if nothing changed.

What operators should expect

  • The same route name should stay the same route.
  • Changing a watch folder should update the route, not make a twin copy.
  • Validation should run again after a meaningful change.
  • Promotion should stay explicit, not automatic.

What safe rerun should never do

  • Duplicate jobs just because setup was repeated.
  • Erase queue files or processing history.
  • Quietly switch a Production route to a different task.
  • Force operators to rebuild the whole workspace for one small update.
Best operator habit When something changes, update the route and validate again. Do not create a second nearly-identical route unless it truly represents different incoming work.

Watch the route name

If a job fails, the route name should tell you what kind of work was affected without opening a config file.

Watch the lane

Draft problems are expected. Production problems need a cleaner response plan and clear ownership.

Watch the last clear signal

Good status messages are human: what arrived, what ran, what failed, and what action the operator should take next.

The product should still keep the two underlying queues. The operator experience should simply present them as understandable workflow lanes instead of raw internals.

6. Operator FAQ

Questions non-technical users should be able to answer quickly.

Can I have many task-and-montage combinations?

Yes. Add more routes. Each route represents one clear combination. You still keep only the two processing lanes.

What if a folder changes later?

Update the route and rerun setup. That should refresh the route definition without duplicating old work.

Should every experiment get its own queue?

No. That makes operations harder. Queues are lanes. Routes are the specific rules for incoming work.

When do I move something to Production?

After Draft behaves predictably and the route is easy to explain. Promotion is a trust step, not a convenience step.

What if I am unsure whether to edit or create a route?

Edit when the route is still the same kind of work. Create a new route only when the incoming files or processing intent are materially different.

What is the core promise of this model?

You can safely repeat setup, understand live routes at a glance, and manage many workflows without drowning in queue details.
