Operator guide

Run serve with routes, not hidden mechanics.

The route-first serve model is built for operators. Define a route once, prove it safely in Draft, then promote the same route into Production. If you run setup again later, the system should update only what changed and leave old work alone.

Draft is the proving lane
Production is the trusted lane
Reruns should be safe and repeatable
If you only remember four things

The operator mental model

Manage routes

A route is the thing you create, review, update, and explain to another person. It represents one kind of incoming work.

Ignore queue internals

Behind the scenes there are still only two lanes. Operators should think in Draft and Production, not raw queue files.

Update, do not duplicate

If a folder or rule changes, update the route. Do not make near-identical copies unless the work is genuinely different.

Backend terms The current backend still uses test and live. In operator language, read those as Draft and Production.

1. Draft vs Production

Use Draft to gain trust. Use Production to stay boring.

Operators need the difference to be obvious. Draft is where you prove that a route is correct. Production is where you expect that route to run without surprises.

Draft

Use this when a route is new or changing

  • Set up the route definition.
  • Validate folders, task choice, montage, and readiness rules.
  • Run dry runs or sample files.
  • Watch for obvious mistakes before anyone depends on it.
Promote when stable →
Production

Use this only after the route is predictable

  • Keep it focused on live, approved work.
  • Prefer small changes over big rewrites.
  • If you need to experiment, step back into Draft first.
  • Every active Production route should be easy to explain.
Simple check If you would feel nervous handing the route to a coworker today, it does not belong in Production yet.
2. Route anatomy

A route is one clear promise about incoming files.

A good route answers one sentence cleanly: “When files like this arrive here, run this task with this montage.” That is the unit that scales cleanly to many workflows.

Every route needs

Core ingredients

Name
Human-readable route label Use the task and montage so the route is recognizable at a glance
Input
Where the files arrive The watched folder or folders for this exact workflow
Task
Which processing recipe runs The experiment-specific workflow to apply
Montage
Which channel layout applies The cap or channel structure expected for these files
Ready rule
When pickup is safe Examples: sidecar present, upload finished, or file size stable
Scaling rule

Many routes, only two lanes.

You can support many task-and-montage combinations without creating many queues. That keeps monitoring understandable for operators.

What not to do

Do not make a queue for every montage.

Queues are operational lanes. Routes are configuration units. Mixing those ideas makes the system harder to run.

Good naming

Name routes so another person can identify them fast.

Example pattern: task name + montage + anything operationally important, such as a lab site or special intake rule.

3. Edit vs create

Most operator confusion comes from this one decision.

When something changes, the safest question is not “How do I patch the queue?” It is “Is this still the same route?” Use this rule before you touch anything.

Edit the existing route when

The work is still the same kind of work

  • The watch folder moved but the task is unchanged.
  • The readiness rule needs tightening.
  • The route name needs cleanup.
  • You are promoting the same route from Draft into Production.
Create a new route when

The incoming work is materially different

  • The task changes to a different experiment or workflow.
  • The montage changes in a way that affects processing intent.
  • The files come from a different intake stream that should be tracked separately.
  • The old route must keep working exactly as it already does.
Operator shortcut If you would need to explain the change as “this is basically a different job,” make a new route. Otherwise, update the existing one.
4. Operator setup path

Build once in Draft, then promote the same route.

This workflow is intentionally repetitive and safe. The current TUI route screen now supports the safe operator actions, but these steps should remain true even if the screen layout changes later.

01

Name the route clearly

Use a label that captures the task and montage so the route makes sense in logs, lists, and handoffs.

02

Choose the intake folder and ready rule

Decide where the files arrive and what counts as complete. This is one of the most important operator safety settings.

03

Select the task and montage

One route should represent one clear task-and-montage combination. Avoid overloading a route with multiple meanings.

04

Compile and validate in Draft

The route registry should build the Draft configuration deterministically and validation should confirm that the route is usable.

05

Exercise the route safely

Use dry runs or sample files until the route does exactly what you expect and the outputs are easy to interpret.

06

Promote to Production

Once the route is stable, promote the same route into Production instead of rebuilding it from scratch.

Current TUI route actions

In the current route screen, operators can inspect one route at a time, toggle whether it is enabled, promote a Draft route into Production, and sync the generated serve configs after route updates.

  • Enter shows the full route details below the table.
  • T enables or disables the selected route.
  • P promotes the selected route into Production.
  • S rebuilds the generated Draft and Production configs from the route registry.
Why the route registry matters Small independent route specs are easier to update safely than one giant hand-edited config file. That is the backbone of the new workflow.
5. Safe reruns

Rerun setup without fear.

Idempotent setup means you can repeat the same workflow later without creating duplicate jobs or wiping prior history. Operators need this because folders, names, and readiness rules inevitably change.

If nothing changed

The route should remain exactly as it was. Re-running setup should behave like a no-op, not a reset.

If a route detail changed

The system should update only that route, then recompile and revalidate the generated Draft or Production config as needed.

If old work already exists

The rerun should leave queue history, outputs, and prior results alone. Setup should not act like a destructive cleanup tool.

What safe rerun means in practice
  • Create the route if it does not exist.
  • Update only the fields that changed.
  • Do nothing visible if the route definition is unchanged.
  • Keep promotion explicit instead of silently changing Production behavior.
What safe rerun should never mean It should never duplicate jobs, clone a second nearly identical route behind your back, or erase prior work just because someone ran setup again.

Watch the route name

The route name should tell you what kind of work was affected without forcing you to open a config file.

Watch the lane

Draft issues are part of proving a route. Production issues usually need faster, more explicit escalation.

Watch the last clear signal

Useful status messages explain what arrived, what ran, what failed, and what action the operator should take next.

7. Handoff checklist

Before you tell someone a route is ready, make sure these are true.

The route is explainable

A teammate can answer what arrives, what task runs, which montage applies, and whether the route is still in Draft or already trusted in Production.

The route is repeatable

Running setup again produces the same result when nothing changed and a targeted update when something did.

The route is not hiding a workaround

If the route only works because of a special manual trick, it is not ready for handoff yet.
