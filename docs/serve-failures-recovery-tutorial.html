Recovery tutorial

Recover from serve problems without turning them into bigger problems.

This page is for the operator moment after setup: something looks wrong, a route is missing, validation fails, or Production no longer feels trustworthy. The goal is to recover safely, not improvise changes that make the state harder to explain.

First principle

Most route problems should be fixed by updating the route definition and validating again.

Second principle

Draft is the proving lane. If Production feels uncertain, step back into Draft.

Biggest risk

Cloning routes, hand-editing generated files, or treating queue files like the source of truth.

Triage first

Before you change anything, answer these three questions.

Is the route still the same job?

If yes, update the route. If no, create a new route instead of warping the old one.

Is this only a Draft issue?

If yes, fix it there first. Do not drag uncertainty into Production.

Can you explain the issue simply?

If you cannot explain it, pause and inspect the route details in the TUI before making changes.

Common failures

Use the symptom, not the panic, to choose the recovery path.

What you see Likely cause Safe recovery
Validation fails right after a route change Bad folder path, bad task path, wrong glob, or invalid route field Rerun serve route upsert with the corrected values, then validate again. Apply only after the Draft config is clean.
The route does not show up in the TUI The route spec was never created, the route id changed, or the registry needs sync Run serve route list, then serve route sync, then reopen or refresh the TUI.
The wrong files are being matched The folder path or file glob is too broad Update the route in Draft only, validate, and dry-run again before trusting it.
A route should stop running for now The route is enabled but should be paused Disable it from the TUI with T or rerun serve route upsert with the route disabled, then use Settings → Apply before processing stops watching it.
Production no longer feels trustworthy A recent change was promoted too early Stop treating Production as the test lane. Reproduce and fix the route in Draft first, then promote again only after it is boring.
Safe recovery commands

These are the boring commands you want in a problem.

List routes
autocleaneeg-pipeline serve route list --path /path/to/serve-workspace
Rebuild generated configs
autocleaneeg-pipeline serve route sync --path /path/to/serve-workspace
Validate Draft again
autocleaneeg-pipeline serve validate --path /path/to/serve-workspace --mode test

Recovery order

  • inspect the route
  • update the route definition if needed
  • sync generated configs if needed
  • validate in Draft
  • apply in Settings when you are ready for processing to use the change
  • only then think about Production
What never to do

These moves create confusion faster than they solve the incident.

Do not patch queue files by hand

Queues are runtime state, not the operator-facing source of truth.

Do not edit generated configs first

serve-test.yaml and serve-live.yaml are compiled outputs. Start with the route registry.

Do not fork a new route for a tiny fix

If it is still the same workflow, update the existing route instead of inventing a duplicate.
